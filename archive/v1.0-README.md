# Akash → dstack v1.0 Real SNP + Unified Binding Integration

This is the first integration package that connects the v0.9 workload-binding
logic to the v0.8 Trustee-backed SEV-SNP verifier contract.

## Architecture

```text
Akash/CoCo SNP evidence
        ↓
RealSnpVerifierAdapter
        ↓
v0.8 Rust/Trustee verifier
        ↓
AMD chain/signature/TCB/VMPL verification
        ↓
REPORT_DATA == workload commitment
        ↓
v1.0 unified workload binding
        ↓
image/config policy
        ↓
VerifiedWorkload
```

## Commitment

```text
SHA256(
  domain ||
  workload_pubkey ||
  image_manifest_digest ||
  resolved_config_digest ||
  verifier_nonce
)
```

The Rust/Trustee verifier receives that 32-byte value as the expected
REPORT_DATA input. Trustee performs the actual SNP cryptographic verification.

## Why the Python bridge is not the trust anchor

Python does not parse AMD certificates or decide whether an SNP signature is
valid. `RealSnpVerifierAdapter` delegates that work to the Trustee-backed Rust
binary and only accepts exit code 0.

This keeps cryptographic hardware verification out of KMS policy logic.

## Real integration

Build the v0.8 Rust verifier:

```bash
cargo build --release
```

Then construct:

```python
RealSnpVerifierAdapter(
    "/path/to/target/release/akash-coco-snp-adapter"
)
```

and use it with `RealCpuUnifiedVerifier`.

## Tests

```bash
python -m unittest discover -s tests -v
```

The included tests use `FakeSnpVerifierAdapter` only so the binding/state
machine can be tested without AMD hardware or network access.

## What still prevents a real Akash test

The guest-side deployment must actually generate fresh SNP evidence where
REPORT_DATA is the v1.0 workload commitment.

A historical Akash quote will correctly fail.

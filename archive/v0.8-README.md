# Akash / CoCo Real SEV-SNP Adapter v0.8

This replaces the v0.7 `MockSnpEvidenceVerifier` concept with a path that delegates
real cryptographic verification to Confidential Containers **Trustee**.

## What it verifies

Trustee's current SNP verifier:

- parses the AMD SEV-SNP report;
- determines the EPYC processor generation;
- obtains/validates VCEK/ASK/ARK material;
- verifies the certificate chain;
- verifies the report signature;
- checks report TCB values;
- requires VMPL 0;
- checks expected `REPORT_DATA`;
- can also check an expected Init-Data hash.

This is much safer than reimplementing AMD verification ourselves.

## Akash input

The adapter accepts the shape already observed from the Akash attestation sidecar:

```json
{
  "report": "<base64 raw SNP report>",
  "cert_chain": "",
  "tee_platform": "snp-gpu"
}
```

The adapter parses the raw report with the `sev` crate and converts it into the
evidence shape expected by Trustee.

When no cert chain is included, Trustee's SNP verifier defaults to AMD KDS for
VCEK retrieval.

## Run

```bash
cargo run --release -- \
  examples/akash-attestation.json \
  <32-byte-workload-commitment-as-hex>
```

The workload commitment is the v0.7 value:

```text
SHA256(
  domain ||
  workload_pubkey ||
  image_manifest_digest ||
  config_digest ||
  verifier_nonce
)
```

Trustee pads/regularizes expected SNP REPORT_DATA as required and verifies it
against the signed report.

## Important limitation

The old Akash attestation captured before we added workload binding will **not**
contain the new v0.7 commitment in REPORT_DATA. It is useful as a parser fixture,
but it should fail the new binding check.

To prove v0.8 end-to-end we need a **new Akash deployment** after the guest-side
v0.6 binding path is actually present. That deployment must generate fresh SNP
evidence using the KMS/verifier nonce and workload commitment.

# Akash → dstack KMS Bridge v0.7

This prototype implements the verifier-side challenge and workload-binding state machine.

## Flow

1. Verifier/KMS issues a random 32-byte nonce and challenge ID.
2. Confidential guest generates/uses its workload public key.
3. Measured guest-side code supplies the trusted `image_digest` and `config_digest`.
4. Guest asks the Attestation Agent for fresh evidence over:

   `H(workload_pubkey || image_digest || config_digest || nonce)`

5. Verifier validates hardware evidence and requires SNP `REPORT_DATA` to match the expected commitment.
6. Verifier enforces image/config/GPU policy.
7. Challenge becomes unusable after one verification attempt.

## Why this matches Trustee/RCAR

Trustee's KBS protocol already uses a Request → Challenge → Attestation → Response flow.
Its challenge contains a nonce for freshness, its runtime data includes the nonce and an
ephemeral TEE public key, and the hash of runtime data is bound into hardware evidence.

Our extension is to include the resolved workload identity (`image_digest` and
`config_digest`) in the value committed to fresh evidence.

## Deliberately unfinished

This version uses `MockSnpEvidenceVerifier` for unit testing. The remaining hard integration is:

- adapt real Akash/CoCo SNP evidence into `EvidenceResult`;
- verify AMD certificate/TCB/reference values;
- verify NVIDIA GPU evidence when required;
- correlate CoCo/Trustee Init-Data and image-pull measurements;
- integrate with the real Trustee/KBS policy path;
- perform real X25519/HPKE/JWE secret wrapping to the attested ephemeral key.

The mock verifier must never be used for actual secret release.
